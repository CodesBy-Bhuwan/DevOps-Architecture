## 🎯 Design Decisions

### 1. Multiple inventories — one per environment

```text
inventory/
├── aws.ini
├── dev.ini
└── prod.ini
```

| Inventory | Purpose | Maintenance |
|---|---|---|
| `aws.ini` | AWS environment | Auto-generated by Terraform |
| `dev.ini` | Local/Vagrant development | Manually maintained or generated |
| `prod.ini` | Production environment | Manually maintained |

The same roles can be reused across environments; the inventory determines **which hosts** are targeted.

Examples:

```bash
ansible-playbook -i inventory/aws.ini playbooks/site.yml
ansible-playbook -i inventory/dev.ini playbooks/site.yml
ansible-playbook -i inventory/prod.ini playbooks/site.yml
```

> `inventory/aws.ini` is generated by Terraform and should not be edited manually.

---

### 2. Environment-specific variables

```text
group_vars/
├── all.yml
├── dev.yml
└── prod.yml
```

`all.yml` contains shared platform values.

`dev.yml` and `prod.yml` provide environment-specific overrides.

This keeps common configuration in one place while allowing environment differences without duplicating the roles.

---

### 3. Host-specific variables

```text
host_vars/
├── master.yml
├── worker1.yml
└── worker2.yml
```

Host variables are used where individual Kubernetes nodes require different values, such as:

- Node role
- API advertise address
- Master address
- Node-specific Kubernetes settings

This avoids placing host-specific configuration into global variables.

---

## 4. Purpose-driven playbooks

Playbooks are grouped by **what they do**, rather than creating one playbook for every role type.

| Category | Purpose | Example |
|---|---|---|
| Top-level | End-to-end deployment | `site.yml` |
| Bootstrap | Initial server preparation | `bootstrap.yml` |
| Provisioning | General server/tool provisioning | `provision.yml` |
| Per-tool | Install/configure one component | `jenkins.yml` |
| Monitoring | Deploy monitoring stack | `monitoring.yml` |
| Integration | Connect already-installed tools | `integrate-tools.yml` |
| Lifecycle | Start/stop/status operations | `playbooks/control/` |

### Why this split?

- `site.yml` → complete platform deployment
- Per-tool playbooks → targeted development/debugging
- Integration playbooks → cross-tool wiring after installation
- Control playbooks → day-2 lifecycle operations without re-running installation

## 5. Control playbooks

```text
playbooks/control/
├── start/
│   ├── all.yml
│   ├── jenkins.yml
│   ├── sonarqube.yml
│   ├── nexus.yml
│   ├── prometheus.yml
│   └── grafana.yml
│
├── stop/
│   ├── all.yml
│   ├── jenkins.yml
│   ├── sonarqube.yml
│   ├── nexus.yml
│   ├── prometheus.yml
│   └── grafana.yml
│
└── status/
    └── all.yml
```

These playbooks manage the lifecycle of **existing containers**.

They are intentionally separate from installation playbooks.

```text
Install/configure
       │
       ▼
Container exists
       │
       ├── start
       ├── stop
       └── status
```

## 6. Integration playbooks

```text
integrate-tools.yml
        │
        ├── Jenkins ↔ SonarQube
        └── Jenkins ↔ Nexus

integrate-monitor.yml
        │
        ├── Prometheus ↔ Grafana
        └── Promtail ↔ Loki ↔ Grafana

integrate-all.yml
        │
        └── Both integration groups
```

### Why separate installation from integration?

Tool installation and cross-tool wiring have different failure points.

Separating them means an integration issue can be retried without reinstalling the services themselves.

---

## 7. Bootstrap vs common

### `bootstrap`

Used for one-time server preparation such as:

```text
bootstrap/
└── tasks/
    ├── main.yml
    ├── hosts.yml
    └── ssh.yml
```

### `common`

Used for baseline configuration shared across normal runs.

Keeping these responsibilities separate prevents one-time setup tasks from being repeated unnecessarily.

---

## 8. Role structure

Roles use the standard Ansible structure where required:

```text
roles/<name>/
├── defaults/main.yml
├── vars/main.yml
├── tasks/main.yml
├── templates/
├── files/
├── handlers/main.yml
└── meta/main.yml
```

### `defaults/` vs `vars/`

| Directory | Purpose |
|---|---|
| `defaults/` | User/environment-overridable values |
| `vars/` | Internal role values |
| `tasks/` | Configuration and installation logic |
| `templates/` | Jinja2-generated configuration |
| `files/` | Static files copied to hosts |
| `handlers/` | Actions triggered by changes |
| `meta/` | Role dependencies |

---

## 9. Role dependencies

Role dependencies are declared in `meta/main.yml`.

Example:

```yaml
dependencies:
  - role: common
```

A tool role can therefore depend on the baseline configuration it requires instead of manually duplicating prerequisites.

The platform's practical dependency chain begins with:

```text
common
   │
   ▼
docker
   │
   ├── jenkins
   ├── sonarqube
   ├── nexus
   ├── prometheus
   ├── grafana
   ├── loki
   └── promtail

kubernetes
   │
   └── Kubernetes node preparation
```

---

## 10. Jenkins is Compose-based

The Jenkins role does **not** use a raw `docker run` template.

Its actual structure is:

```text
roles/jenkins/
├── files/
│   ├── docker-compose.yml
│   ├── plugins.txt
│   └── casc/
│       └── jenkins.yml.backup
│
├── templates/
│   └── jenkins.yml.j2
│
└── tasks/
    ├── main.yml
    ├── install.yml
    ├── plugins.yml
    ├── casc.yml
    ├── configure.yml
    ├── jobs.yml
    ├── github.yml
    └── service.yml
```

This is documented in detail in [`jenkins-structure.md`](jenkins-structure.md).

## 🔁 Top-level execution flow

The complete platform is orchestrated from `playbooks/site.yml`.

Conceptually:

```text
bootstrap
    │
    ▼
docker
    │
    ├── Jenkins
    ├── SonarQube
    ├── Nexus
    ├── Monitoring
    └── Kubernetes preparation
            │
            ▼
       integrate-all
```

The exact ordering remains defined by the actual playbook imports and role dependencies.

## 🧩 Extensibility

### Add a new tool

A new component should normally have:

```text
roles/<tool>/
playbooks/<tool>.yml
playbooks/control/start/<tool>.yml
playbooks/control/stop/<tool>.yml
```

Then add it to the appropriate integration playbook and `site.yml` when it belongs to the full platform deployment.

### Add a new environment

1. Add the inventory under `inventory/`.
2. Add environment-specific variables under `group_vars/`.
3. Reuse existing roles wherever possible.
4. Avoid duplicating tool configuration for each environment.
